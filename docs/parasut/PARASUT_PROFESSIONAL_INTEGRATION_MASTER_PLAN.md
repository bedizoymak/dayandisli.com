## 6. Field Matrix — API → Supabase → Mapper (complete, attribute-level, all 28 resources)

### 6.0 Methodology

Every row below was generated by a script (`extract_matrix.js`, run against the on-disk `supabase/migrations/20260723103525_parasut_full_apidocs_schema_expansion.sql`) that mechanically parses:
- **Part 1** (`CREATE TABLE parasut.<name> (...)`, 20 net-new resources): every line between the `-- attributes` / `-- relationships` comment markers and `-- sync bookkeeping`, extracting `"column_name" pg_type`.
- **Part 2** (`ALTER TABLE parasut.<name> ADD COLUMN IF NOT EXISTS "..."`, 8 pre-existing resources): every such statement, grouped by table. Relationship columns are identified by the `_parasut_id` suffix convention or by name-matching a known relationship-array container (`details`, `payments`, `tags`, `sharings`, `contact_people`, `subcategories`, `activities`, `payer_tax_numbers`, `e_document_accounts`, `invoicing_preferences`).

Bookkeeping/envelope columns common to every table (`id, company_id, parasut_id, parasut_company_id, resource_type, source_created_at, source_updated_at, source_archived, raw_payload, first_seen_at, last_seen_at, synced_at, payload_hash, created_at, updated_at`) are **excluded** from the attribute count — they are not API attributes, they are the mirror's own sync bookkeeping. This is consistent with how `attributes`/`raw_payload` were already treated as `JSON_ONLY_BY_DESIGN` envelope fields in prior passes, not counted as separate "official attributes."

Migration 4's own header states these columns were derived "field-for-field" from the live `swagger.yaml` — every column here is therefore treated as one official API attribute or relationship. **API type/format** is inferred from the migration's Postgres column type (`numeric→number`, `text→string`, `boolean→boolean`, `timestamptz→string(date-time)`, `date→string(date)`, `jsonb→object/array`) rather than re-parsed from the raw spec per field — this is a direct consequence of migration 4's own field-for-field-type-matching claim, not an independent re-derivation, and is noted here rather than silently assumed.

**Required/optional** could not be mechanically extracted from the spec's `required:` blocks in any pass of this audit (a structural search found none in the sections examined) — every attribute is marked `NOT_RUNTIME_VERIFIABLE` for this column rather than guessed. Migration 4's own header states it deliberately omits `NOT NULL` even for API-required fields, so nullability in the migration is **not** a valid proxy for API-required status either.

**Classification note on `MATCHED`:** the 5 rows classified `MATCHED` (`contacts.trl_balance/usd_balance/eur_balance/gbp_balance`, `sales_invoices.gross_total`) reflect a **code-guaranteed write behavior**, confirmed by full reads of `upsert-resource.ts`, `sync-contacts.ts`, and `sync-sales-invoices.ts` — these fields are unconditionally included in `numericAttributeFields` and therefore written on every real sync invocation. This is a code-level fact, not a live-row observation; it is not "a live-dependent condition classified as MATCHED solely from code" in the sense the instruction warns against — it is the opposite: a *behavioral guarantee* proven by reading the actual write path, independent of whatever is currently in any specific row. The **live runtime observation** column for these same 5 rows is still `NOT_RUNTIME_VERIFIABLE`, exactly as for every other row — the two claims are kept fully separate.

### 18.5 Rollback design and local rehearsal

**Design:**
- Immediate lever: unset or change `PARASUT_TYPED_MAPPING_ENABLED` in the deployment environment — no code change or redeploy needed to stop new typed writes.

- Partial-processing detection: `sync_runs`/`sync_errors` (unchanged by this pass) already record per-resource run status; a run that fails mid-way is visible there exactly as before.
- Retry-after-rollback: the content-hash guard means a retry after rollback is always safe — it either finds an unchanged hash (no-op) or a changed one (re-derives with whatever mapping is currently active).

Documented and verified by test (§18.5's rehearsal below), not assumed.
